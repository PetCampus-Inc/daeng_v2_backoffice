# 0014. 인증 세부 결정

## 맥락

[ADR 0008](0008-session-cookie-auth.md)은 서버 세션과 HttpOnly 쿠키로 정하면서 구글 로그인 흐름, CSRF 방어, 세션 만료
시간, 역할 모델을 서버 구현 때 정하기로 했다. 로그인을 구현하기 전에 정한다.

## 결정

- **로그인 흐름:** 웹이 구글 로그인 버튼(Google Identity Services)으로 받은 ID 토큰을 `POST /auth/login`으로 보낸다.
  서버는 토큰만 검증한다(서명, 발급자, 우리 클라이언트 ID, 만료, 이메일 인증 여부). 허용 여부는 등록된 이메일로
  판단한다(대소문자 구분 없음). 서버가 구글로 리다이렉트하고 콜백을 받는 방식은 쓰지 않는다.
- **세션:** 요청이 없는 채로 24시간이 지나면 만료하고, 요청할 때마다 연장한다. 최대 유지 기간은 두지 않는다. 세션 ID는
  추측할 수 없는 무작위 값이며 BO 전용 DB에는 해시로 저장한다. 로그아웃하거나 계정을 비활성화하면 해당 세션을 지운다.
- **쿠키:** 이름 `session`, `HttpOnly`, `Secure`(HTTPS 환경), `SameSite=Lax`, `Path=/`, `Domain`은 지정하지 않는다.
- **CSRF:** `SameSite=Lax`와 쓰기 요청(POST·PUT·PATCH·DELETE)의 `Origin` 확인으로 막는다. `Origin`이 허용 목록(웹
  주소)과 다르거나 없으면 403(`FORBIDDEN`)으로 거부한다. 허용 목록은 설정값으로 둔다. 웹과 서버가 같은 출처(`/api`
  프록시)라는 전제다.
- **역할:** 역할 3종(`SUPER_ADMIN`, `OPERATOR`, `VIEWER`)을 코드 상수로 두고, 가드가 요청마다 역할과 계정 상태를
  확인한다. 권한 테이블은 두지 않는다.

## 근거

- ID 토큰 방식은 리다이렉트 주소와 state 처리가 없어 구현이 단순하다. 토큰은 서버로 한 번 보내 검증하고 저장하지 않는다.
- 무활동 24시간 만료와 최대 유지 기간 없음은 기획 요구사항(FR-BO-012)이다.
- 세션 ID를 해시로 저장하면 DB가 노출돼도 세션을 그대로 쓸 수 없다.
- 사내 도구이고 웹과 서버가 같은 출처이면 `SameSite=Lax`와 `Origin` 확인으로 충분하다. 다른 사이트의 쓰기 요청에는
  쿠키가 붙지 않고, `Origin` 확인이 이를 한 번 더 막는다. 프론트와 명세를 바꿀 필요가 없다.
- 역할이 3종으로 고정이고 기능별 권한이 기획 표로 정해져 있어 권한 테이블은 과하다.

## 검토한 대안

- 서버 콜백(OAuth 코드 흐름): 토큰이 자바스크립트에 노출되지 않지만 리다이렉트 주소와 state 처리, 로그인 API 변경이
  필요하다.
- CSRF 토큰: 가장 강하지만 모든 쓰기 요청에 헤더를 붙여야 해서 프론트와 명세가 바뀐다.
- 절대 만료 시간 추가: 기획이 최대 유지 기간을 두지 않는다.
- 권한 DB 테이블: 역할이 고정이라 과하다.

## 결과와 후속

- 구글 클라이언트 ID(웹)를 발급하고 승인된 JavaScript 원본에 개발·운영 주소를 등록한다. 서버는 클라이언트 ID를 환경
  변수로 받는다.
- 웹과 API가 서로 다른 사이트가 되면 CSRF 토큰 방식으로 바꾸고 새 ADR을 쓴다.
- `/api` 프록시: 개발은 웹 개발 서버 프록시, 배포는 리버스 프록시로 `/api`를 서버에 전달한다. 설정은 프론트와 배포
  작업에서 한다.
- 첫 로그인 프로필 설정 완료 전에는 `/me`, 프로필 저장, 로그아웃 외의 API를 서버가 403 `PROFILE_INCOMPLETE`로
  막는다(구현됨).
- 현재 명세(`POST /auth/login`, 요청 `idToken`)와 같아서 명세 변경은 없다.
