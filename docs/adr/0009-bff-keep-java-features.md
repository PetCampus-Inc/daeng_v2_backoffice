# 0009. 기존 Java 기능은 이전하지 않고 호출

## 맥락

백오피스 기획(5.10)에는 기존 어드민의 대시보드, 회원, 유치원, 원장 인증 현황, 체크인 화면이 "요구사항 변경 없이 구현
그대로" 유지하는 것으로 들어 있다. 서비스 DB(MySQL)는 개발과 운영이 분리되어 있지 않고 운영 DB 하나뿐이다.

## 결정

- Node 서버(`apps/server`)가 프론트의 단일 창구가 된다. 프론트는 이 서버만 호출한다.
- 로그인, 팀원 계정, 변경 이력, 알림(5.1~5.4, 5.9)처럼 BO 고유 기능은 Node 서버가 BO 전용 DB로 직접 처리한다. BO 전용
  DB는 MySQL이고, 서비스와 같은 서버의 별도 database와 별도 계정을 쓴다.
- 서비스 데이터는 Node로 이전하지 않는다. **읽기**는 서비스 DB를 읽기 전용 계정으로 직접 조회한다(기존 `daeng-admin`
  방식). **쓰기**(문의 답변, 공지 게시·수정, 약관 등록·공개·철회 등)는 Java API를 호출한다. 호출 대상은 지금 운영 중인
  v1 API다.
- Java에 BO가 필요한 규칙이나 API가 없으면 Java에 추가한다.
- 응답은 [API 공통 규약](../api-conventions.md)의 형식으로 변환한다. 서비스 DB의 날짜는 KST로 저장돼 있으므로 UTC로
  바꿔서 준다.

## 근거

- 요구사항이 바뀌지 않는 기능을 다시 만들어도 사용자에게 가치가 없다.
- 운영 DB 하나를 공유하는 환경에서 잘 동작하는 기능을 다시 짜면 서비스 데이터에 영향을 줄 위험만 생긴다.
- 호출과 변환은 이전보다 작업량이 훨씬 작다.
- 읽기는 기존 화면(대시보드·회원·유치원·원장 인증 현황)이 이미 SQL 조회로 구현돼 있고, 목록·검색 API를 Java에 모두 새로
  만드는 것보다 작업이 적다. 읽기 전용 계정이라 서비스 데이터를 바꿀 수 없다.
- 쓰기는 앱도 같은 데이터를 읽으므로 검증 규칙을 Java 한 곳에 둔다. 두 서버가 같은 테이블에 쓰면 규칙이 둘이 되고, 운영
  DB가 하나뿐이라 실수의 피해가 크다.
- 나중에 특정 기능을 Node로 옮기고 싶어도 프론트 변경 없이 서버 내부만 바꾸면 된다.
- 프론트가 형식 하나만 알면 되므로 기존 Java 형식과 신규 형식을 함께 처리하는 부담이 없다.

## 검토한 대안

- 기존 기능을 Node로 이전: 위 이유로 제외했다.
- Node 없이 Java에 BO 기능을 모두 추가: 가능하지만 서비스와 무관한 BO 고유 기능을 서비스 코드베이스에 섞게 되고,
  프론트와 타입을 공유할 수 없다.
- 읽기·쓰기를 모두 Java API로: BO가 DB 구조를 몰라도 되지만 목록·검색·통계 API를 Java에 모두 만들어야 한다.
- 읽기·쓰기를 모두 서비스 DB 직접: BO 서버만으로 구현할 수 있지만 규칙이 두 곳에 생기고 서비스 스키마 변경에 취약하다.

## 결과와 후속

- 서비스 DB 읽기 전용 계정을 발급하고, BO 서버가 배포된 곳에서 서비스 DB에 닿는 네트워크 경로를 확인한다.
- 문의·제안 데이터가 서비스 DB의 어느 테이블에 있는지 확인한다. [확인 필요]
- BO 서버가 Java API를 호출할 때의 인증 방식(서버 간 인증)과 키 보관 방식을 정한다.
- v1에 BO 규칙이 없는 쓰기(공지 상태 필터·마크다운·초안 삭제, 약관 시행일 규칙·초안 삭제 등)는 Java 작업으로 따로
  등록한다.
- 서비스 DB의 PK(BIGINT)가 자바스크립트 안전 정수 범위를 넘지 않는지 확인한다. 명세는 ID를 정수로 준다.
- BO 전용 DB를 만들고 기존 화면 4종의 조회를 BO 서버에 구현한다.
