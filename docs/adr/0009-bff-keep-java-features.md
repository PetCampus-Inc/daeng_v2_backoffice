# 0009. 기존 Java 기능은 이전하지 않고 호출

## 맥락

백오피스 기획(5.10)에는 기존 어드민의 대시보드, 회원, 유치원, 원장 인증 현황, 체크인 화면이 "요구사항 변경 없이 구현
그대로" 유지하는 것으로 들어 있다. 서비스 DB(MySQL)는 개발과 운영이 분리되어 있지 않고 운영 DB 하나뿐이다.

## 결정

- Node 서버(`apps/server`)가 프론트의 단일 창구가 된다. 프론트는 이 서버만 호출한다.
- 로그인, 팀원 계정, 변경 이력, 알림(5.1~5.4, 5.9)처럼 BO 고유 기능은 Node 서버가 BO 전용 DB로 직접 처리한다.
- 기존 Java 기능은 Node로 이전하지 않는다. Node 서버가 Java를 호출하고, 응답을 [API 공통 규약](../api-conventions.md)의
  형식으로 변환해 프론트에 준다.

## 근거

- 요구사항이 바뀌지 않는 기능을 다시 만들어도 사용자에게 가치가 없다.
- 운영 DB 하나를 공유하는 환경에서 잘 동작하는 기능을 다시 짜면 서비스 데이터에 영향을 줄 위험만 생긴다.
- 호출과 변환은 이전보다 작업량이 훨씬 작다.
- 나중에 특정 기능을 Node로 옮기고 싶어도 프론트 변경 없이 서버 내부만 바꾸면 된다.
- 프론트가 형식 하나만 알면 되므로 기존 Java 형식과 신규 형식을 함께 처리하는 부담이 없다.

## 검토한 대안

- 기존 기능을 Node로 이전: 위 이유로 제외했다.
- Node 없이 Java에 BO 기능을 모두 추가: 가능하지만 서비스와 무관한 BO 고유 기능을 서비스 코드베이스에 섞게 되고,
  프론트와 타입을 공유할 수 없다.

## 결과와 후속

아직 정하지 않았다(상태 "제안"인 이유).

- 문의, 공지, 약관 데이터가 서비스 DB에 있는지 BO 전용 DB에 둘지. 서비스 DB에 있으면 쓰기는 Java API로 하는 쪽이
  안전하다.
- 서비스 DB를 직접 읽을지, 읽는다면 읽기 전용 계정을 쓸지. 운영 DB 하나뿐이므로 읽기 전용 계정을 권장한다.
- 기존 Java 화면의 호출 방식과 신규 BO API의 주소 구분(현재 웹 기본 주소는 `/api/v0/platform-admin` 하나다).
- 서비스 DB를 직접 읽을 때 날짜 컬럼의 시간대와 PK 타입(BIGINT) 처리.
