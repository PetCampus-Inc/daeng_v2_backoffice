# 0019. BO 개발 서버

## 맥락

BO 서버는 운영 한 곳에만 배포되고 있었다([ADR 0018](0018-bo-server-deploy.md)). v1 서비스는 2026-11-06에 개발 AWS 계정
(`294556736127`)을 따로 두고 `dev` 푸시는 개발 서버, `main` 푸시는 운영 서버로 배포하도록 나눴다. BO도 머지 전에 실제
서버에서 확인할 곳이 필요하다.

## 결정

- **서버**: v1 개발 서버(EC2 `i-0368d89a37823af9e`, t3.small)에 BO 컨테이너를 함께 올린다. 운영과 같은 스크립트, 같은
  메모리 한도(300MB), 같은 도커 네트워크(`ec2-user_default`)를 쓴다.
- **배포 흐름**: `Deploy Server` 워크플로 하나가 브랜치로 대상을 고른다. `dev`는 개발 계정, `main`은 운영 계정이다. 각
  배포 역할은 자기 브랜치에서 실행된 워크플로만 받아 준다.
- **개발 계정 자원**: ECR 저장소, 배포 역할(`knockdog-backoffice-dev-deploy`), 서버 역할의 BO 이미지 받기 권한을 BO
  저장소의 CloudFormation 템플릿(`infra/bo-server-deploy.yml`, 스택 `knockdog-backoffice-dev`)으로 만든다. 서버·스테이징
  버킷·OIDC 제공자는 v1의 `knockdog-base` 스택 것을 쓰고, 그 스택의 정책은 고치지 않고 별도 정책을 붙인다.
- **주소**: API 원본은 `dev-bo.knockdog.net`이다. 개발 웹(S3·CloudFront)은 서버가 동작하는 것을 확인한 뒤 따로 만든다.
- **환경 변수**: BO Infisical 프로젝트의 `staging` 환경을 쓴다. `dev`는 로컬 개발용이다.

## 근거

- v1 개발 서버는 사용 가능 메모리가 약 733MB(2026-11-25 측정)라 300MB 한도의 BO를 더 올릴 수 있다. 서버를 새로 만들면
  비용이 늘어난다.
- 워크플로를 하나로 두면 운영과 개발의 배포 단계가 어긋나지 않는다.
- 템플릿으로 두면 무엇을 만들었는지 코드로 남고, 지울 때 스택만 지우면 된다.
- Infisical 환경 이름을 v1과 맞추면(개발 서버 `staging`, 로컬 `dev`) 헷갈리지 않고, 로컬 값과 서버 값(DB 호스트 등)이
  섞이지 않는다.

## 검토한 대안

- 개발용 워크플로 파일을 따로 두기(v1 방식): 단계가 거의 같은 파일 두 개를 함께 고쳐야 한다.
- CLI로 자원 직접 만들기(운영 방식): 빠르지만 무엇을 만들었는지 추적하기 어렵다.
- v1 `knockdog-base` 스택에 BO 자원 추가: 한 스택에 모이지만 v1 저장소 변경이 필요하고 서버가 있는 스택을 바꾸는 위험이
  있다.
- 서버와 웹을 한 번에: 확인할 것이 많아 서버를 먼저 띄운다.

## 결과와 후속

- 세션 쿠키 때문에 웹과 API가 같은 주소여야 하므로([ADR 0008](0008-session-cookie-auth.md)), 개발 웹을 만들 때 운영처럼
  CloudFront `/api/*`를 `dev-bo.knockdog.net`으로 보낸다. 그 전에는 개발 서버를 `/health`와 Swagger로만 확인한다.
- 개발 서버 디스크는 16GB다. BO 배포 스크립트는 옛 이미지를 정리하지만, 마이그레이션 이미지(1GB 이상)를 받는 동안 여유가
  필요하다.
- 운영 계정 자원은 이 템플릿 이전에 손으로 만들었다. 운영도 템플릿으로 옮길지는 따로 정한다.
