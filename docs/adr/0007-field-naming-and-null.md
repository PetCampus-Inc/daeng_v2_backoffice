# 0007. 필드 이름과 null 처리

## 맥락

JSON 필드 이름과 값이 없을 때의 표현을 정해야 프론트 타입과 서버 DTO가 어긋나지 않는다. 특히 부분 수정(PATCH)에서는
필드를 보내지 않는 것과 `null`을 보내는 것이 다른 뜻이어야 한다.

## 결정

- 필드 이름은 camelCase다. 약어는 첫 글자만 대문자로 쓰고(`userId`, `apiKey`), 불리언은 `is`나 `has`로 시작한다.
- 응답은 필드를 생략하지 않는다. 값이 없으면 `null`이다. 빈 문자열과 `null`을 같은 뜻으로 쓰지 않는다.
- PATCH 요청에서 보내지 않은 필드는 변경하지 않고, `null`을 보낸 필드는 값을 삭제한다.

## 근거

- 서버와 프론트가 모두 TypeScript라서 이름을 변환 없이 같게 쓸 수 있고, Java 서비스 플랫폼도 camelCase가 기본이다. DB
  컬럼이 snake_case여도 ORM에서 매핑하면 API 규칙과 무관하다.
- 응답 필드가 항상 존재하면 모양이 예측 가능하고, 명세에서 `nullable`로 표현해 타입이 `string | null`로 정확해진다.
  Prisma나 TypeORM 같은 ORM도 nullable 컬럼을 `null`로 돌려준다.
- PATCH에서 생략과 `null`을 구분하지 않으면 "보내지 않았는데 지워졌다"나 "지우려고 `null`을 보냈는데 무시됐다"는 버그가
  난다.
- "없음"을 `null`과 빈 문자열 두 가지로 쓰면 검색과 통계가 틀어진다.

## 검토한 대안

snake_case는 JS 관례와 어긋나고 코드 스타일 린트와 충돌할 수 있다. 값이 없을 때 필드를 생략하는 방식은 응답마다 모양이
달라지고 `undefined`와 `null`을 모두 처리해야 한다.

## 결과와 후속

enum 값의 표기(`ACTIVE` 또는 `active`)는 아직 정하지 않았다. 첫 명세를 쓰기 전에 정한다. `packages/shared`의
`JOB_ROLES`는 화면 표시용 문구(`'풀스택'`)이므로 API enum 값과 같은 개념을 따로 정의하지 않도록 enum을 정할 때 함께
정리한다.
