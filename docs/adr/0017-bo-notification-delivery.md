# 0017. BO 알림의 수신 시점과 이벤트 전달

## 맥락

새 문의·추가 문의·제안은 Java에서 저장되고 운영자 계정과 알림은 BO DB에 있다. 두 저장소는 같은 트랜잭션으로 묶을 수
없다. Java 또는 BO의 일시적인 장애가 알림 누락이나 중복으로 이어지지 않아야 한다. 디스코드는 Java가 보낸다.

PRD 7장은 이벤트 발생 시점의 활성 계정을 수신자로 정하지만, 2026-10-30 사용자와 BO가 이벤트를 처음 처리할 때의 활성
계정과 역할을 기준으로 변경하기로 합의했다. 기획 원문의 반영 여부는 별도로 확인한다.

## 결정

- Java는 업무 데이터와 BO에 전달할 이벤트를 같은 트랜잭션에 저장한다. 별도 메시지 큐는 도입하지 않는다.
- 담당자 변경도 같은 방식이다. Java가 행 잠금 안에서 확정한 이전 담당자 ID와 변경한 사람 ID를 이벤트에 담는다. BO가 Java
  응답을 받아 알림을 만들지 않는다.
- BO 서버는 1개로 운영한다고 전제한다. BO는 완료되지 않은 이벤트를 약 10초마다 ID 순서로 최대 50건씩 가져온다. 각 조회
  순회는 처음부터 시작한다. 선점·만료는 두지 않는다. 같은 이벤트가 두 번 와도 이벤트 ID 유일 제약으로 한 번만 처리되므로
  서버가 늘어도 안전하다.
- 이벤트 하나가 계속 실패해도 뒤의 이벤트가 무기한 대기하지 않도록 처리한다. 실패와 복구 상태를 운영자가 확인할 수 있게
  한다. 완료된 이벤트는 30일 뒤 삭제하고 미완료는 지우지 않는다. 가장 오래된 미완료 이벤트가 5분을 넘으면 경보한다.
- 알림에 보여 줄 변경한 사람의 표시명·직무는 알림을 만들 때의 값을 저장한다. 나중에 바뀌어도 문구는 유지한다.
- 담당자 변경 알림은 담당자가 실제로 바뀌었고 이전 담당자가 있으며 활성일 때만 만든다. 담당 해제와 최초 담당은 만들지
  않는다.
- BO가 Java 이벤트를 가져와 최초 처리할 때 BO DB에서 활성 계정과 역할을 조회한다. 이벤트 처리 기록과 수신자별 알림은
  같은 BO DB 트랜잭션으로 저장한다. 수신자가 없어도 처리 기록을 저장한다.
- Java의 고유 이벤트 ID를 BO의 중복 처리 방지 키로 사용하고 DB 유일 제약으로 보장한다. 다시 받은 이벤트는 수신자를
  재계산하지 않는다.
- BO DB 커밋 후 Java에 완료를 알린다. 완료 요청 실패·응답 유실 시 이벤트를 재전달하고 BO는 처리 기록을 확인해 중복 생성
  없이 완료 요청을 재시도한다. Java의 반복 완료 요청도 안전하게 처리한다.
- 디스코드는 Java가 새 문의·추가 문의를 접수할 때 보낸다. BO는 디스코드를 보내지 않는다. Java는 문의 저장과 같은
  트랜잭션에 발송 기록을 남기고 워커가 전달한다. 실패하면 최대 5회 시도하며 간격은 60초부터 2배씩 늘어 최대 900초이고,
  429는 `Retry-After`를 따른다. 최종 실패는 보존하고 로그·지표로 알린다. BO 알림 저장과 독립이다.
- 디스코드 성공 응답이 유실되면 같은 메시지가 중복될 수 있다. 드물다고 보고 알려진 한계로 둔다.
- 배포된 디스코드 문구에는 문의 제목이 들어 있다. PRD FR-BO-102의 "사용자 정보·본문 없이"에 맞는지 기획에 확인한다.

## 근거

디스코드를 Java가 보내는 이유: 접수 직후 나가며 BO가 멈춰도 팀이 알 수 있고, BO에 웹훅 비밀과 발송 기록을 따로 둘 필요가
없다. 발송 기록을 DB에 두므로 서버가 재시작돼도 이어서 보낸다. 디스코드는 팀이 보는 채널이고 사용자별로 남기는 기록은 BO
알림이다.

DB에 이벤트를 함께 남기면 업무 저장과 이벤트 발생 사이의 누락을 줄일 수 있다. BO가 처리한 기록을 트랜잭션으로 보관하면
완료 확인 실패나 중복 전달을 복구할 수 있다. 현재는 큐의 추가 운영 없이 필요한 신뢰성을 구현한다.

## 검토한 대안

- Java의 직접 HTTP 호출만 사용: BO 장애나 프로세스 중단 때 전달 누락을 복구할 별도 기록이 필요하다.
- BO가 업무 테이블의 변경을 직접 추론: 데이터 구조에 의존하고 개별 추가 문의의 감지·누락 복구가 어려워진다.
- 요청 안에서 즉시 재시도만 하고 포기: 서버가 죽거나 재시작되면 그 건이 사라져 발송 기록과 워커 방식을 택했다.
- 메시지 큐: 향후 소비자·운영 요구가 늘면 검토한다. 큐만으로 DB 저장과 메시지 전송의 원자성이나 소비자 중복 처리가
  해결되지는 않는다.
- 발생 시점 수신자: 현재 BO 계정 이력만으로 최초 로그인 등 모든 상태를 정확히 복원하기 어렵다. 사용자와 처리 시점
  기준으로 변경했다.

## Java 이벤트 v1 계약

[daeng_v1_back PR #492](https://github.com/PetCampus-Inc/daeng_v1_back/pull/492)로 배포된 계약이며 Java 코드 기준으로
확인했다.

- 내부 접두어: `/api/v0/platform-admin/bo-notification-events`, 인증 헤더: `X-Backoffice-Api-Key`.
- `GET`은 `limit`(기본·최대 50)과 선택적인 `afterId`를 받고 Java 응답 래퍼의 `data.items`와 `data.nextAfterId`를
  반환한다. 미완료 이벤트를 ID 오름차순으로 페이지 조회하고 다음 조회 순회는 처음부터 시작한다.
- `POST .../complete`는 `{ "eventIds": [123] }`(1~50개, 중복 없는 양의 정수)를 받는다. 모두 존재하면 이미 완료된 ID를
  포함해도 204다. 알 수 없는 ID가 있으면 404이고 전부 롤백한다. 입력이 잘못되면 400이다. 완료된 이벤트만 30일 뒤
  삭제되므로 방금 조회한 미완료 이벤트를 완료할 때 404가 날 일은 사실상 없다.
- 이벤트는 `eventId`(양의 정수, JSON 숫자), `schemaVersion: 1`, `type`, `targetType`, `targetId`, `messageId`,
  `previousAssigneeId`, `actorMemberId`, UTC `occurredAt`을 포함한다. 숫자 대상·팀원·메시지 ID는 JS 안전 정수 범위다.
  추가 문의만 `messageId`, 담당자 변경만 이전 담당자·변경자 ID를 가지며 나머지는 null이다.
- 종류는 `NEW_INQUIRY`, `ADDITIONAL_INQUIRY`, `ASSIGNEE_CHANGED`, `NEW_IDEA`다. 마지막의 대상은 `IDEA`, 나머지는
  `INQUIRY`다. 사용자 정보나 본문은 포함하지 않는다.
- Java가 실패 이벤트를 반복 반환하더라도 BO는 같은 조회 순회에서 뒤 페이지를 처리한다. 최대 20페이지 처리 후 다음 주기에
  이어 읽고, 마지막 페이지를 지나면 다음 순회를 처음부터 시작한다. Java의 재전달·완료 계약은 실제 서버와 대조한다.

- 보관·경보: 완료된 이벤트는 30일 뒤 삭제하고 미완료는 지우지 않는다. Java가 5분 넘은 미완료 이벤트를 오류 로그와 지표로
  남긴다.

## 결과와 후속

- Java 이벤트 조회·완료 API의 v1 계약은 위 절에 기록했다. BO 서버가 붙은 DB에 마이그레이션을 먼저 적용한 뒤
  `NOTIFICATION_POLL_ENABLED=true`로 폴링을 켠다. 여러 BO 서버가 같은 Java를 읽으면 이벤트를 나눠 가져가므로 알림을 받을
  환경에서만 켠다.
- 디스코드 문구의 문의 제목 포함 여부를 기획에 확인하고, Java의 5분 경보(로그·지표)가 실제 경보 수단에 연결됐는지
  확인한다.
- 수신자 정책 변경을 공유 PRD에 반영할 담당자와 절차를 확인한다.
