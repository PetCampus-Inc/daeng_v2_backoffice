# 0008. 인증은 세션 쿠키

## 맥락

로그인은 구글 로그인이고, 등록된 팀원 계정만 접근한다(5.1, 5.2). 세션 만료와 계정 비활성화를 지원해야 한다. 서비스
사용자의 인증과는 별개의 팀원용 인증이다.

## 결정

로그인 후 서버 세션을 만들고 세션 ID를 HttpOnly 쿠키로 보낸다. 프론트는 axios에 `withCredentials: true`를 설정하고
토큰을 직접 다루지 않는다. 세션 저장소는 BO 전용 DB의 테이블로 시작한다.

## 근거

- 계정을 비활성화하면 세션을 지워 접근을 바로 막을 수 있다. 세션 만료도 서버가 완전히 통제한다.
- 사내 도구이고 서버가 하나라서 JWT의 장점(stateless, 서버 확장)이 필요하지 않다.
- HttpOnly 쿠키는 자바스크립트가 읽을 수 없어 XSS에 강하고, 프론트 구현이 `withCredentials` 한 줄이다.

## 검토한 대안

JWT: 토큰이 만료될 때까지 유효해서 즉시 차단하려면 차단 목록이 필요하고, 재발급 로직과 토큰 보관 방식을 직접 설계해야
한다.

## 결과와 후속

- 쿠키는 프론트와 서버의 주소 관계에 민감하다. 개발과 배포 모두 `/api` 프록시로 같은 출처처럼 맞추는 것을 서버 세팅 때
  확정한다.
- CSRF 방어 방식, 구글 로그인 흐름(서버가 콜백을 처리할지 프론트가 토큰을 전달할지), 세션 만료 시간, 역할(권한) 모델은
  서버 구현 때 정한다.
- 현재 `apps/web/src/api/client.ts`에는 인증 설정이 없다("로그인 방식을 정한 뒤 붙인다").
