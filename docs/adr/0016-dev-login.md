# 0016. 개발용 로그인

## 맥락

[ADR 0014](0014-auth-details.md)의 구글 ID 토큰 로그인은 프론트 로그인 화면이 있어야 시험할 수 있다. 화면이 아직 없고,
구글 클라이언트 ID 설정(승인된 JavaScript 원본 등) 없이도 인증이 필요한 API를 시험할 수 있어야 한다. 구글 연동 자체는
실제 계정으로 한 번 확인했다. v1에도 `GET /auth/dev/{id}`라는 개발용 로그인이 있다.

## 결정

- `POST /auth/dev-login`(`{ email }`)을 둔다. 등록된 팀원의 이메일로 구글 검증 없이 세션을 만든다. 등록 여부,
  비활성·등록 취소 거부, 세션 발급, 접속 기록은 구글 로그인과 같은 코드를 쓴다.
- `DEV_LOGIN_ENABLED=true`일 때만 켜진다. 기본은 꺼짐이고, 꺼져 있으면 입력과 상관없이 `404`다.
- 쿠키 `Secure`가 켜진 설정(운영)에서 켜면 서버가 시작하지 않는다. 운영에서 실수로 켜져 인증이 뚫리는 것을 막는
  안전장치다.
- **서버와 같은 컴퓨터(127.0.0.0/8, ::1)에서 온 요청만 받는다.** 다른 컴퓨터에서 온 요청은 꺼져 있을 때와 똑같이
  `404`다. 구글 로그인과 세션 쿠키 인증은 열쇠(토큰, 쿠키)가 있지만 개발용 로그인은 이메일만 알면 되고, `Origin` 검사는
  curl 같은 프로그램이 흉내 낼 수 있어서 방어가 되지 않기 때문이다.
- 명세에 `개발용` 태그로 넣어서 Swagger에서 `Try it out`으로 부른다. 프론트도 로컬에서 쓸 수 있다.
- 켜진 채 시작하면 서버 로그에 경고를 남긴다.

## 근거

- 인증이 필요한 모든 API를 시험하려면 로그인이 먼저인데, 구글 로그인만 있으면 화면과 구글 설정에 매번 의존한다.
- 우회 기능은 위험하므로 기본 꺼짐, 운영 설정에서 시작 거부, 같은 허용 규칙 재사용으로 범위를 좁혔다.

## 검토한 대안

- Swagger 화면에 구글 로그인 버튼을 주입(먼저 만들었다가 제거): 구글 클라이언트 ID에 `localhost:3000`을 등록해야 하고
  직접 유지해야 하는 스크립트가 늘어서 제거했다.
- 사용자 PK로 로그인(v1 방식): 이메일이 더 읽기 쉽고 등록 여부 확인을 그대로 재사용할 수 있다.

## 결과와 후속

- 접속 기록에는 구글 로그인과 같은 `LOGIN_SUCCESS`로 남는다. 개발 환경에서만 쓰이는 기능이라 따로 구분하지 않았다.
- 한계: 다른 컴퓨터나 Docker 컨테이너에서 이 서버의 개발용 로그인을 호출할 수 없다(컨테이너에서 호스트로 오는 요청의
  출발지는 loopback이 아니다). 필요해지면 허용 주소를 설정으로 늘린다. 쿠키 `Secure` 검사는 "HTTPS가 아님"이지 "운영이
  아님"이 아니라서 HTTP로 서비스하는 스테이징에서는 이 안전장치만으로 막히지 않는다. 스테이징에서는
  `DEV_LOGIN_ENABLED`를 켜지 않는다.
- 운영 배포 전 확인: 운영 환경에 `DEV_LOGIN_ENABLED`가 없거나 `false`이고 `COOKIE_SECURE=true`인지.
