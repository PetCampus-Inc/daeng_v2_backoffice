# 0015. 서버 응답은 테스트에서 명세로 검증

## 맥락

[ADR 0003](0003-api-spec-first.md)에 따라 OpenAPI YAML이 계약의 원천이다. 프론트는 PR #3에서 "구현이 바뀌면 명세도 함께
갱신되는가"를 요청했다. 구현과 명세는 따로 쓰이므로 사람이 챙기지 않으면 어긋난다. 첫 실제 API(로그인)를 만들면서 방법을
정했다.

## 결정

- 서버 테스트는 실제 HTTP 응답을 `packages/api-spec/openapi.yaml`의 해당 API·상태 코드에 정의된 응답 스키마로 검사한다
  (`apps/server/test/support/openapi-contract.ts`, `expectMatchesSpec`). 개발 전용 패키지 `ajv`, `ajv-formats`를 쓴다.
- 검사하는 것: 정의되지 않은 API·상태 코드, 본문이 있어야 하는지 없어야 하는지, 필드 누락·타입·enum 값·`nullable`,
  최상위의 정의에 없는 필드. 중첩 객체의 정의에 없는 필드는 검사하지 않는다.
- 새 API를 만들면 성공 응답과 명세에 적은 오류 응답을 `expectMatchesSpec`으로 검사하는 테스트를 같이 쓴다. 쓰기 요청
  API는 `Origin` 검사로 403이 나올 수 있으므로 명세에 403을 적어야 한다(검사가 알려 준다).
- 개별 API 응답으로 적기 어려운 공통 오류(없는 주소 404 등)는 `checkSchema('Error', body)`로 공통 `Error` 형식만
  검사한다.
- DB 없이 확인할 수 있는 응답은 기본 테스트(`pnpm test`)에서, DB가 필요한 응답은 CI의 `server-db-test` 작업에서 돈다.
- 명세의 모든 응답 스키마가 이 검사 도구로 해석되는지도 테스트로 확인한다.

## 근거

- 명세와 실제 응답을 직접 대조해서, 필드 이름·타입·오류 코드가 어긋나면 테스트가 실패한다. 로그인 구현 중에 명세에 없던
  `400`과 `FORBIDDEN` 403 응답을 이 검사가 찾았다.
- 요청 처리 코드와 상관없이 응답만 보므로 NestJS 구현 방식을 바꿔도 그대로 쓸 수 있다.

## 검토한 대안

- 명세에서 서버용 타입을 생성(`openapi-typescript` 등): 컴파일 때 반환 타입은 맞출 수 있지만 상태 코드, 오류 본문,
  응답이 명세와 같은지는 확인하지 못하고 생성 파일을 관리해야 한다.
- `@apidevtools/swagger-parser`: 저장소의 최소 Node 버전(22.18)보다 높은 22.19를 요구해서 쓰지 않았다.
- 직접 만든 검사 코드: 스키마 해석을 다시 만들어야 해서 오류 위험이 크다.

## 결과와 후속

- 웹이 orval로 타입을 생성하는 것은 별개다. 웹은 명세를 소비하고, 서버는 테스트로 명세를 지킨다.
- OpenAPI 3.0의 `nullable`은 검사 도구가 JSON Schema로 바꿔서 해석한다. 명세에서 `nullable`을 `allOf`·`oneOf`와 함께
  써도 된다.
