# 0013. API 문서는 서버가 YAML을 Swagger UI로 제공

## 맥락

[ADR 0003](0003-api-spec-first.md)에 따라 OpenAPI YAML이 계약의 원천이다. 명세가 3,000줄을 넘어 YAML을 직접 읽는
것만으로는 검토하기 어렵고, `$ref`로 흩어진 요청·응답을 한눈에 보는 문서 화면이 팀 전체에 필요하다. 서버에는 아직
`GET /health`만 구현되어 있다.

## 결정

- 서버가 `API_DOCS_ENABLED=true`일 때 `/docs`에서 YAML을 Swagger UI로 보여 준다. 문서 JSON(`/docs-json`)은 열고 YAML
  주소는 열지 않는다.
- 문서는 YAML을 그대로 읽어서 만든다. 컨트롤러에서 명세를 따로 생성하지 않는다.
- 로컬에서는 `apps/server/.env`(커밋되지 않음)로 켤 수 있다. 서버가 시작할 때 `.env`를 읽되 이미 설정된 환경 변수는
  덮어쓰지 않고, 운영은 배포 환경의 환경 변수를 쓴다.
- 기본값은 꺼짐이고, 값은 `true`·`false` 문자열만 받는다. 켠 상태에서 명세 파일을 읽을 수 없으면 서버가 시작하지 않는다.
- `Try it out`은 끈다. 구현되지 않은 API를 호출하게 하지 않기 위해서이고, 구현이 늘면 다시 판단한다.
- 명세 폴더를 `@daeng/api-spec` 워크스페이스 패키지로 만들어, 서버가 패키지 이름으로 파일을 찾는다.
- 운영·스테이징에서 문서를 공개할지는 이 ADR에서 정하지 않는다. 정하기 전에는 켜지 않는다.

## 근거

- 팀원이 서버만 켜면 같은 주소에서 같은 문서를 볼 수 있다. 개인 에디터 확장이나 별도 도구가 필요 없다.
- YAML을 그대로 읽으므로 문서와 계약이 어긋날 수 없다. 코드에서 문서를 만드는 방식은 ADR 0003과 맞지 않는다.
- 패키지 이름으로 찾으면 개발 실행, 빌드 결과 실행, 다른 위치에서의 실행, 서버만 따로 배포하는 경우에도 같은 파일을
  가리킨다. 빌드 때 파일을 복사하는 방식은 저장소 바깥 파일이라 설정이 번거롭다.
- 기본을 꺼 두면 켜지 않은 환경에서 내부 API 구조가 노출되지 않는다. 켜지 않으면 문서 도구(`@nestjs/swagger`)를
  불러오지도 않는다.
- 문자열 `'false'`를 `true`로 바꾸는 `z.coerce.boolean()` 대신 `'true'`·`'false'`만 허용해 설정 실수를 시작 오류로
  드러낸다.

## 검토한 대안

- 컨트롤러에서 `@nestjs/swagger`로 명세를 생성: ADR 0003의 YAML 원천과 어긋난다.
- 별도 도구로 정적 HTML을 만들어 공유: 서버와 따로 관리되고 최신 상태를 보장하기 어렵다.
- GitHub Pages 공개: 비공개 저장소여도 공개될 수 있어 내부 API 명세에 맞지 않는다.
- 항상 켜 둠: 운영 노출 여부를 정하지 않은 상태에서 위험하다.

## 결과와 후속

- 서버 구현이 늘면 `Try it out` 활성화를 판단한다. 명세와 실제 응답의 일치 검증은
  [ADR 0015](0015-spec-contract-tests.md)에서 테스트로 한다.
- 운영·스테이징 공개 여부와 접근 제한을 정한다.
- 주소 접두어는 `/api/v0/admin`으로 정해졌고, `/docs`와 `/health`는 접두어 밖에 둔다.
- `@nestjs/swagger`가 가져오는 `@scarf/scarf`는 설치 스크립트가 사용 통계를 보낸다. pnpm 10의 기본 설정이 이를 막고
  있으므로 `pnpm approve-builds`로 허용하지 않는다.
