# 0003. API는 명세를 먼저 쓴다

## 맥락

프론트는 orval로 OpenAPI 명세에서 요청 함수, 타입, TanStack Query 훅, mock 응답을 생성할 계획이다. 프론트와 서버가
동시에 개발을 시작한다.

## 결정

OpenAPI(YAML) 명세를 먼저 작성한다. 명세 PR을 먼저 머지한 뒤 프론트와 서버가 각자 구현한다. 명세가 API 요청·응답 타입의
유일한 원천이며, 같은 타입을 `packages/shared`에 따로 정의하지 않는다.

## 근거

- 서버가 완성되기 전에도 프론트가 mock 응답으로 화면을 만들 수 있어 병렬 개발이 된다.
- 화면마다 필요한 API를 시작 전에 합의하므로 나중에 필드가 없어서 생기는 재작업이 줄어든다.

## 검토한 대안

- 코드에서 명세를 자동 생성: 명세와 구현이 어긋날 일은 적지만 프론트가 서버 컨트롤러가 나올 때까지 기다리거나 임시
  코드를 써야 한다.
- 명세 없음: 프론트가 요청 코드와 타입을 직접 쓴다.

## 결과와 후속

- 서버 구현이 명세에서 벗어날 위험이 있다. 서버 코드가 안정되면 코드에서 명세를 생성하는 방식으로 바꾸거나, 구현을
  명세와 대조하는 검증과 명세 린트(Spectral)를 CI에 추가하는 것을 검토한다.
- 명세 파일의 위치(후보: `packages/api-spec`)와 분리 방식은 첫 명세를 쓰기 전에 정한다. 기능이 열 개 안팎이라 처음부터
  도메인별로 나누는 쪽이 낫다.
- 현재 `apps/web`의 가짜 API는 직접 작성한 것이다. 첫 명세는 이 가짜 API의 요청·응답을 출발점으로 삼을 수 있다.
