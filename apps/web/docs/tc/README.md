# TC (테스트 케이스)

BO 1단계의 테스트 케이스다. **AI가 이 문서를 읽고 테스트 코드를 만들고**, 사람은 만들어진 테스트와 이 문서를 함께
검토한다.

- 근거: `.local/docs/prd/KD3-578.md`(개인 로컬 문서, 이하 PRD). TC 제목 끝 괄호는 PRD의 절 번호나 FR 번호다.
- 기능 요구사항 TC에 PRD에 없는 동작을 지어 넣지 않는다. PRD가 정하지 않아 결정이 필요한 곳은 `(보류: …)`로 표시했다.
  사용성 검증과 사용자 피드백에 따른 회귀 사례는 별도 묶음으로 기록하고 근거를 명시한다.

## 세 층

| 층              | ID              | 무엇                                                                                           | 테스트 방식                                  |
| --------------- | --------------- | ---------------------------------------------------------------------------------------------- | -------------------------------------------- |
| 규칙 층(R)      | `R-<규칙명>-NN` | 화면 없이 입력 → 출력으로 확인하는 요구사항 규칙(권한, 상태 전환, 이탈 판정, 글자 수, 검증 등) | Vitest 단위 테스트. 표 한 줄 = 경우 하나     |
| 화면 동작 층(S) | `S-<기능>-NNN`  | 준비 상태 1개 + 행동 1개 + 그 결과 확인 여러 개                                                | `실행:` 줄에 따라 E2E / 브라우저 확인 / 수동 |
| 흐름 층(F)      | `F-<기능>-NN`   | 여러 화면·여러 단계를 잇는 시나리오(PRD 3장 흐름)                                              | 모두 Playwright E2E                          |

기능 약칭은 파일마다 하나다: `공통`(00), `내계정`(01), `팀원`(02), `문의`(03), `제안`(04), `공지`(05), `약관`(06),
`알림`(07), `이력`(08), `로그인`(09), `홈`(10), `회원`(11), `유치원`(12), `인증`(13).

## 규칙 층(R) 양식

```markdown
## R-문의상태. 문의 상태 전환 (5.2)

| ID            | 현재 상태 | 현재 담당자 | 일어난 일 | 다음 상태 | 다음 담당자 |
| ------------- | --------- | ----------- | --------- | --------- | ----------- |
| R-문의상태-01 | 답변 대기 | 미배정      | 맡기      | 확인 중   | 나          |
```

- Vitest `test.each`에 표를 그대로 넣는다. **ID 열 다음의 열은 모두 입력값이거나 기대값**이다. 설명용 열은 두지 않는다.
- 표 위 한 줄에 어느 열이 입력이고 어느 열이 기대값인지 적었다. 설명이 필요하면 표 아래 목록으로 따로 적었다.
- 판정 위치가 서버인 규칙(알림 받는 사람, 변경 이력 기록, 접속 기록, 로그인 판정 등)은 표 위에 `판정: 서버`라고 적었다.
  BO 프론트에 판정 코드가 없으면 가짜 API(MSW) 핸들러가 이 규칙대로 동작하는지 Vitest로 확인하고, 실제 서버 동작은 같은
  파일의 `실행: 수동` S TC로 확인한다.
- 칸 값 `—`는 해당 없음이다.
- 칸에 `(보류: …)`가 든 줄은 기대값이 정해지지 않은 경우다. `test.each`에서 건너뛴다(`test.skip`).
- 다른 표나 묶음을 입력으로 쓰는 표(예: 입력 칸이 `` `문의-기본` ``)는 `fixtures.md`의 그 묶음 데이터를 입력으로 넣는다.

## 화면 동작 층(S) 양식

```markdown
### S-문의-029. 미배정 문의를 맡는다 (FR-BO-053)

- 실행: E2E
- 로그인: 운영자
- 데이터: `문의-기본`
- 시작: 문의 상세(#1041)
- 행동: [내가 맡기] 클릭
- 확인:
  - 토스트 `문의를 맡았습니다.`
  - 상태 배지 '확인 중'
```

| 줄        | 필수   | 뜻                                                                                                                                 |
| --------- | ------ | ---------------------------------------------------------------------------------------------------------------------------------- |
| `실행:`   | 예     | `E2E` / `브라우저 확인` / `수동 (이유)` 중 하나. 아래 [실행 방식](#실행-방식)                                                      |
| `로그인:` | 예     | [`fixtures.md`](fixtures.md)의 계정 이름. 로그인하지 않은 상태면 `없음`                                                            |
| `데이터:` | 아니오 | `fixtures.md`의 데이터 묶음 이름. `팀원-기본`은 항상 깔려 있어 적지 않는다                                                         |
| `시각:`   | 아니오 | 지금 시각을 기준 시각(2026. 10. 07. 10:00 KST)과 다르게 둘 때                                                                      |
| `창:`     | 아니오 | 브라우저 창 폭. 없으면 1440px                                                                                                      |
| `API:`    | 아니오 | 가짜 API 응답을 묶음 정의와 다르게 줄 때. 예: `답변 저장 요청이 500 응답`. 응답 형식(상태 코드·본문)은 API 스펙에 맞춰 정한다      |
| `시작:`   | 예     | 처음 여는 화면. PRD에 주소가 있으면 주소(`/home`), 없으면 화면 이름(`문의 상세(#1041)`). 주소는 지어내지 않고 실제 라우트에 맞춘다 |
| `준비:`   | 아니오 | 행동 전에 해 둘 화면 조작                                                                                                          |
| `행동:`   | 예     | 확인할 행동 하나                                                                                                                   |
| `확인:`   | 예     | 행동 뒤에 확인할 결과. 백틱 안 글자는 화면 문구 그대로                                                                             |

- **경우마다 따로**: `로그인`·`API`·`창`·`시각`·`시작`·`준비`·`행동` 중 한 줄에 `(경우마다 따로)`를 붙이고 아래에 여러
  줄을 나열하면, 경우마다 같은 TC를 따로 실행한다(`test.each`나 반복문). 경우별 확인 값은 그 줄 끝에 `→ 결과`로 적었고,
  `확인:`에는 모든 경우에 공통인 것만 적었다.
- `행동` 줄이나 준비 줄의 `A → B`는 'A를 한 뒤 B 상태가 된다'는 뜻이다. `확인:` 안의 '이어서 …'는 같은 테스트에서 이어서
  한 번 더 확인하는 것이다.
- R 표를 가리키는 S TC(예: `R-문의검색 표의 검색어를 입력`)는 그 R 표의 줄마다 경우를 만든다.
- 화면 정적 구성(표 열 순서, 안내 글자, 배치)은 "화면을 열었을 때" TC로 묶었다. 이때 `행동:`은 `화면을 연다`다.
- 권한 표 전체는 `00-공통.md`의 R-권한에만 있고, 화면별로는 대표 확인(권한 없는 역할이 들어가면 권한 없음 화면)만 둔다.
- 공통 정책이 그 화면에 적용되는 경우(이탈 확인창, 조회 실패, 저장 실패, 경합 등)는 그 화면의 S TC로 구체적으로 적었다.

## 흐름 층(F) 양식

```markdown
### F-문의-01. 맡아서 답하고 추가 문의를 받는다 (3.3)

- 로그인: 운영자 / 데이터: `문의-기본`

1. 문의 상세(#1041)에서 [내가 맡기] → 확인 중
2. 답변 입력 후 [답변 저장] → 답변 도착
3. (가짜 API) 사용자 추가 문의 등록 → 목록에서 답변 대기, 담당자 나
```

- 단계마다 `행동 → 확인`이다. `(가짜 API)`는 앱 사용자 쪽에서 생기는 일을 가짜 API 상태로 만든다는 뜻이다.
- 흐름은 모두 Playwright E2E다. 가짜 API는 흐름 안에서 바뀐 상태를 이어서 기억해야 한다.

## 실행 방식

S TC마다 `실행:` 줄이 하나 있다.

| 표시                  | 기준                                                                                                                        | 남기는 것                                            |
| --------------------- | --------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------- |
| `실행: E2E`           | 상태가 바뀌거나 데이터가 저장·삭제되는 동작, 경합(다른 사람이 먼저 처리), 저장·조회 실패 처리, 권한·세션으로 막히는 동작    | Playwright 테스트 코드                               |
| `실행: 브라우저 확인` | 문구·배치·표 열 구성·빈 상태 표시·안내 글자처럼 한 번 보면 되는 것                                                          | 코드는 남기지 않는다. 개발할 때 AI가 브라우저로 확인 |
| `실행: 수동 (이유)`   | 코드로 확인할 수 없는 것: 실제 구글 로그인, 사용자 앱에서 보이는 결과, 디스코드 도착, 실제 서버 저장소 확인, 기존 화면 회귀 | 사람·AI가 직접 확인                                  |

- 한 TC에 두 성격이 섞이면 E2E로 표시하고 확인 항목은 상태·저장 결과 위주로 두었다. 순수 문구·배치 확인은 따로 '브라우저
  확인' TC로 나눴다.
- 브라우저 뒤로 가기·새로고침·beforeunload 경고·Esc·주소 직접 입력·창 크기·시각 고정·네트워크 끊김은 Playwright로 할 수
  있으므로 수동이 아니다.
- R 규칙은 모두 Vitest다. F 흐름은 모두 E2E다.

### 사용성 검증 TC와 확인 기록

화면 작업에는 [기여 가이드](../../../../CONTRIBUTING.md#화면-작업의-사용성-검증과-완료-기준)의 사용성 검증을 함께
적용한다. 기능 결과를 확인하는 TC만으로 화면 검증을 끝내지 않는다.

- 화면의 각 상호작용에서 시각적 연속성, 반응·진행 상태, 입력·포커스·스크롤, 상태 일관성, 실패 복구, 조작 가능성 중
  해당되는 위험을 찾는다. 목록뿐 아니라 화면 이동·폼·모달 등에도 적용한다.
- TC는 `준비 조건 → 조작 → 진행 중 기대 결과 → 완료·실패 후 기대 결과`를 포함한다. 첫 방문·재방문, 정상·지연 응답, 빠른
  연속 조작처럼 결함이 드러날 조건을 구체적으로 적는다.
- 기대 결과는 사용자에게 보이는 현상으로 작성한다. 예: 검색 입력 중 커서가 유지되고 마지막 검색어의 결과가 표시된다.
  특정 훅이나 DOM 유지 여부 자체를 모든 화면의 공통 기대값으로 삼지 않는다.
- 중간 상태는 DOM·위치·포커스 관찰, 영상·연속 프레임 등 적절한 방법으로 확인한다. 최종 스크린샷만으로 깜빡임이 없다고
  판정하지 않는다. 자동 판정 가능한 항목은 테스트로, 지각적 품질은 브라우저 확인으로 구분한다.
- PRD가 아닌 공통 품질 기준·사용자 피드백이 근거이면 해당 근거와 날짜를 명시한다. 화면별 결함의 재현 TC도 남긴다.

완료 시 다음 형식으로 확인 기록을 남긴다. 화면별 모든 점검 관점을 포함하고, 해당하지 않는 항목에는 사유를 적는다. 자동
테스트와 브라우저 관찰을 구분하며 테스트 경로·실행 명령·관찰 자료 등 재확인할 근거를 기록한다.

| 항목·TC          | 판정                             | 방법·근거 또는 사유                                             |
| ---------------- | -------------------------------- | --------------------------------------------------------------- |
| 확인 대상과 조건 | 통과 / 실패 / 미확인 / 해당 없음 | 자동 테스트 또는 브라우저 확인의 근거, 실행 제한 또는 제외 사유 |

사용성 검증은 개발 완료 전에 수행한다. 확인 기록과 관찰 자료는 `.local/test-results/`에 보관하며 공유용 결과 폴더를 따로
만들지 않는다. TC와 재실행 가능한 검사 코드는 공유 대상이다.

문서의 체크 항목은 작업 완료 기준이다. CI의 기계적인 차단은 저장소에 등록된 테스트와 CI 설정으로 별도 구현해야 하며, 이
문서만으로 자동 실행되거나 CI가 차단된다고 보고하지 않는다.

## fixtures 쓰는 법

- 테스트를 시작할 때 `데이터:`의 묶음과 `팀원-기본`을 가짜 API에 넣고, `로그인:` 계정의 세션으로 시작한다.
- 묶음 여러 개를 쉼표로 적으면 함께 넣는다(예: `문의-기본`, `알림-기본`).
- `API:` 줄은 묶음을 넣은 뒤 그 요청의 응답만 바꾼다.
- TC의 확인 값(번호, 이름, 시각, 목록 순서)은 묶음 정의에서 나온다. 묶음을 바꾸면 그 묶음을 쓰는 TC의 확인 값도 함께
  고친다.
