## R-알림대상. 알림 받는 사람 (8장, FR-BO-101, 060)

판정: 서버. 입력: 일어난 일, 조건. 기대값: BO 알림 받는 사람, 디스코드. 계정은 `팀원-기본` 기준.

| ID            | 일어난 일             | 조건                                  | BO 알림 받는 사람                           | 디스코드 |
| ------------- | --------------------- | ------------------------------------- | ------------------------------------------- | -------- |
| R-알림대상-01 | 새 1:1 문의 접수      | —                                     | `최고관리자`, `운영자`, `운영자2`           | 보냄     |
| R-알림대상-02 | 사용자 추가 문의      | 담당자 `운영자`(활성), 상태 답변 대기 | `운영자`                                    | 보냄     |
| R-알림대상-03 | 사용자 추가 문의      | 담당자 `운영자`(활성), 상태 확인 중   | `운영자`                                    | 보냄     |
| R-알림대상-04 | 사용자 추가 문의      | 담당자 `운영자`(활성), 상태 답변 도착 | `운영자`                                    | 보냄     |
| R-알림대상-05 | 사용자 추가 문의      | 미배정                                | (없음)                                      | 보냄     |
| R-알림대상-06 | 사용자 추가 문의      | 담당자 `비활성팀원`                   | (없음)                                      | 보냄     |
| R-알림대상-07 | 문의 담당자 변경      | 이전 담당자 `운영자2`(활성)           | `운영자2`                                   | 안 보냄  |
| R-알림대상-08 | 문의 담당자 변경      | 이전 담당자 `비활성팀원`              | (없음)                                      | 안 보냄  |
| R-알림대상-09 | 미배정 문의 맡기      | —                                     | (없음)                                      | 안 보냄  |
| R-알림대상-10 | 새 아이디어 제안 접수 | —                                     | `최고관리자`, `운영자`, `운영자2`, `조회자` | 안 보냄  |
| R-알림대상-11 | 리뷰 신고 접수        | —                                     | (없음)                                      | —        |

- 받는 사람은 일이 생긴 시점의 활성 계정이다. '등록됨'·'등록 취소'·'비활성' 계정에는 만들지 않는다.
- 같은 문의에 추가 문의가 두 번 오면 알림도 두 번 생긴다.
- 이미 생긴 알림은 받은 사람의 역할이 바뀌어도 남는다. 비활성이었다가 재활성화돼도 비활성 동안의 알림은 생기지 않는다.
- 리뷰 신고는 앱이 접수할 때 디스코드로 보내므로 BO 알림이 없다.

## 알림 센터 (7.14)

### S-알림-001. 알림 팝오버를 연다 (FR-BO-100)

- 실행: 브라우저 확인
- 로그인: 운영자
- 데이터: `알림-기본`, `문의-기본`, `제안-기본`
- 시작: `/home`
- 행동: 상단바 알림 아이콘 클릭
- 확인:
  - 아이콘 숫자 `3`
  - 아래로 폭 380의 팝오버
  - 머리 `알림` + 오른쪽 `모두 읽음`
  - 최근순 4건(`fixtures.md` 순서), 항목 = 주황 점(안 읽음) · 문구 한 줄 · 시각
  - 2번(담당자 변경)은 점 없이 회색
  - 시각은 KST 공통 형식

### S-알림-002. 문의 알림을 누른다 (FR-BO-100)

- 실행: E2E
- 로그인: 운영자
- 데이터: `알림-기본`, `문의-기본`, `제안-기본`
- 시작: `/home`
- 준비: 알림 팝오버를 연다
- 행동(경우마다 따로):
  - 1번 `새 1:1 문의가 등록되었습니다. 문의 #1041` → 문의 상세(#1041)
  - 4번 `담당 중인 문의에 추가 문의가 왔습니다. 문의 #1050` → 문의 상세(#1050)
  - 3번 `새 아이디어 제안이 등록되었습니다. 제안 #350` → 제안 상세(#350)
  - 2번(이미 읽음) → 문의 상세(#1045), 숫자 `3` 그대로
- 확인:
  - 경우별 상세로 이동한다
  - 다시 팝오버를 열면 누른 항목이 읽음(점 없음·회색), 안 읽은 항목을 눌렀으면 아이콘 숫자 `2`

### S-알림-003. 볼 수 없는 대상의 알림을 누른다 (7.14)

- 실행: E2E
- 로그인: 조회자
- 데이터: `알림-기본`, `문의-기본`, `제안-기본`
- 시작: `/home`
- 준비: 알림 팝오버를 연다
- 행동: 1번 `새 1:1 문의가 등록되었습니다. 문의 #1041` 클릭
- 확인:
  - `처리가 완료되었거나 볼 수 없는 항목입니다.` 안내
  - 문의 상세로 이동하지 않는다
  - 1번이 읽음이 되고 아이콘 숫자 `2`

### S-알림-004. 해결 완료 문의 알림을 누른다 (7.14, OQ-P13 확정)

- 실행: E2E
- 근거: 2026-10-23 사용자 결정. 해결 여부와 관계없이 접근 가능한 문의의 알림은 상세로 이동한다.
- 로그인: 운영자
- 데이터: `알림-기본`, `문의-기본`
- 시작: `/home`
- 준비: 1번 알림의 대상을 해결 완료 문의 #1048(내 담당) / #1049(미배정)로 바꾼다(각각 독립 실행)
- 행동: 알림 팝오버에서 해당 문의 알림 클릭
- 확인:
  - 읽음 처리 후 해당 문의 상세로 이동하고 미읽음 숫자가 3에서 2로 줄어든다
  - 문의 본문·기존 답변과 '해결 완료' 상태를 확인할 수 있다
  - 답변 입력·답변 저장·내가 맡기·담당자 변경·담당 해제를 제공하지 않는다
  - 팝오버를 다시 열면 해당 알림은 읽음이다. 새로고침 후에도 읽음과 읽기 전용 상세가 유지된다

### S-알림-005. 모두 읽음 (FR-BO-100)

- 실행: E2E

  - 아이콘 숫자가 사라진다

  - 토스트가 뜨지 않는다

### S-알림-006. 읽음은 사람마다 따로다 (8장)

- 실행: E2E
- 로그인: 운영자
- 데이터: `문의-기본`
- 시작: `/home`

- 확인:

### S-알림-007. 알림이 하나도 없다 (7.14)

### S-알림-008. 작성 중에 알림을 눌러 [나가기]를 고른다 (7.14, 4.6)

- 실행: E2E

- 행동: [나가기] 클릭
- 확인:

  - 3번이 읽음, 아이콘 숫자 `2`

## 알림 생성 (8장)

### S-알림-009. 새 문의가 오면 알림이 생긴다 (8장)

- 실행: E2E
- 로그인: 운영자
- 데이터: `문의-기본`
- 시작: `/home`
- 행동: (가짜 API) 앱에서 새 문의 #1051 접수 후 화면을 새로 연다
- 확인:
  - 아이콘 숫자 `1`
  - 팝오버 맨 위 `새 1:1 문의가 등록되었습니다. 문의 #1051`(안 읽음)

### S-알림-010. 담당자 변경 알림 문구에 바꾼 사람 이름이 들어간다 (8장)

- 실행: E2E
- 로그인: 운영자2
- 데이터: `문의-기본`
- 시작: `/home`
- 행동: (가짜 API) `운영자`가 #1045를 [내가 맡기] → [담당자 변경] 한 뒤 화면을 새로 연다
- 확인:

### S-알림-011. 서버가 알림 받는 사람을 규칙대로 정한다 (8장)

- 실행: 수동 (서버 확인 — 실제 서버의 알림 생성은 가짜 API로 확인할 수 없다)
- 상태: 실제 서버 연동 대기(OQ-D12). 모의 수신자 규칙 검사는 실제 전달 검증으로 집계하지 않는다.
- 로그인: 최고관리자, 운영자, 운영자2, 조회자(각각)
- 시작: 실제 개발 서버
- 행동: R-알림대상 표의 일을 앱·BO에서 실제로 일으킨다
- 확인:
  - 각 계정의 알림 센터가 R-알림대상 표의 받는 사람과 같다
  - 역할을 바꿔도 이미 받은 알림이 남는다

### S-알림-012. 디스코드 팀 채널로 알림이 간다 (FR-BO-102)

- 실행: 수동 (디스코드 도착 확인)
- 상태: 실제 서버·디스코드 연동 대기(OQ-D12).
- 로그인: 없음
- 시작: 실제 개발 서버, 디스코드 팀 채널
- 행동: 앱에서 새 1:1 문의와 추가 문의를 등록하고, BO에서 담당자를 바꾸고, 앱에서 새 제안을 등록한다
- 확인:
  - 새 문의·추가 문의(미배정 포함)는 팀 채널 하나에 온다
  - 담당자 변경·새 제안은 디스코드로 오지 않는다
  - 개인 멘션이 없다
  - 문구에 사용자 이름·연락처 같은 사용자 정보와 문의 본문이 없다

## 사용성 검증 (2026-10-22)

근거: 사용자 요청에 따른 전체 TC 누락 점검 및
[웹 테스트 가이드](../testing-guide.md#화면-작업의-사용성-검증과-완료-기준). 기존 기능 TC를 보완하는 조작 품질 기준이다.
PRD OQ 결정 대기 항목의 기대값이나 새로운 PRD 기능을 확정하지 않는다. 실행 조건에 별도 표시가 없으면 정상 응답과 1.5초
지연 응답을 각각 적용하고 첫 방문·재방문을 따로 확인한다. 자동 판정은 E2E로, 깜빡임·배치의 지각적 품질은 전환 중
DOM·위치·포커스·스크롤 관찰과 trace를 함께 보고 판단한다. TC 작성은 검증 통과를 뜻하지 않는다. 실행 결과·항목별
판정·관찰 자료는 Git에서 제외된 로컬 검증 결과 폴더에 남긴다.

적용 범위: 팝오버 조회·읽음·모두 읽음·대상 이동·이탈 확인. 검색·페이지·본문 작성은 없으므로 해당 없음. 해결 완료 문의
알림은 읽음 처리 후 읽기 전용 상세로 이동한다(OQ-P13, 2026-10-23 확정). 실제 알림 생성·디스코드는 별도 수동 TC를 따른다.

구현 전 위험 구체화(2026-10-22): 상단바 최초 조회는 미확정 숫자를 0으로 표시하지 않는다. 재개방·지연 조회 중에는 같은
계정의 목록과 스크롤을 유지한다. 읽음 요청 중 재클릭을 막고 실패 시 읽음 수를 보존하며 목록 안에서 재시도한다. 모두 읽음
완료로 버튼이 사라지면 목록으로 초점을 옮긴다. 이탈 취소는 읽음 요청을 보내지 않고 작성 위치로 복귀한다. 조회자에게 남은
과거 문의 알림·삭제된 대상을 누르면 현재 화면을 유지한다. 390px에서는 긴 문구를 줄바꿈하고 내부 스크롤·Esc·바깥
클릭·초점 복귀 및 가로 넘침을 확인한다. 자동 검사 경로: `apps/web/e2e/notifications-usability.mjs`.
