# 웹 테스트 가이드

이 문서는 `apps/web/`에서 선택한 검사를 수행하고 완료 여부를 판정하는 절차를 정의한다. TC 분류·ID·양식·데이터 준비
방법은 `test-case-writing-rules.md`에서 확인한다. TC 작성 규칙은 여기서 반복하지 않는다.

## 진행 순서

**변경 영향 확인 → 관련 TC 선택 → 선택한 R·S·F 검증 → 실패 수정·재확인 → 결과 기록·완료 판정**

R·S·F는 TC의 분류다. 모든 작업에서 세 분류를 모두 실행하거나 정해진 순서대로 전부 반복하라는 뜻은 아니다.

| 분류         | 확인하는 것                                        | 진행 방법                                            |
| ------------ | -------------------------------------------------- | ---------------------------------------------------- |
| 규칙(R)      | 입력에 따른 권한·검증·상태 전환 결과               | 변경된 로직과 관련된 Vitest 검사                     |
| 화면 동작(S) | 한 화면의 조작 결과, 진행 상태, 실패 복구와 사용성 | 해당 TC의 `실행:`에 따라 E2E·브라우저 확인·수동 확인 |
| 흐름(F)      | 단계·화면 사이에서 이어지는 상태와 사용자 흐름     | 변경이 영향을 주는 흐름을 Playwright E2E로 확인      |

예를 들어 순수 검증 함수만 바꾸면 관련 R 검사를 먼저 고른다. 저장 후 화면 전환이 바뀌면 해당 S와 영향을 받는 F를 고른다.
기존 결과로 충분히 확인된 항목은 재사용하고, 이번 변경으로 달라진 부분만 추가 확인한다.

## 검증 범위 선정

웹 검증 범위는 **변경 사항 → 영향받는 동작 → 필요한 검사** 순서로 정한다. TC는 기능의 전체 기준이며, 매 작업에서 전체
TC를 다시 실행하라는 뜻이 아니다. 검사 명령은 범위를 정한 뒤 선택한다.

### 1. 변경과 직접 영향을 받는 동작 확인

- 실제 diff와 기존 검증 결과를 확인한다. 수정한 동작, 직접 영향을 받는 사용처, 충돌 해결로 달라진 동작을 대상으로
  고른다.
- 공통 코드 변경은 실제 사용처를 확인하고 공통 경로를 대표 사례로 검사한다. 권한·구현 경로에 차이가 있으면 해당 차이를
  추가 확인한다. 공통 코드를 바꿨다는 이유만으로 모든 화면을 검사하지 않는다.
- 같은 브랜치·화면에 속하거나 실행 가능한 검사가 많다는 이유로 관련 없는 항목을 추가하지 않는다. 다른 패키지 검사는 그
  패키지의 동작에 직접 영향이 있을 때만 포함한다.

예를 들어 인증을 헤더에서 세션으로 바꾸면 로그인 복원·권한·세션 만료와 수정한 API 호출 경로를 확인한다. 표 유지·첨부
이미지 배치·검색 조작에 영향을 준다는 근거가 없으면 해당 사용성 검사를 추가하지 않는다.

### 2. 필요한 검사 선택과 기존 결과 재사용

- 기존 검사로 변경된 동작을 확인할 수 있으면 사용하고, 부족한 경우에만 검사를 추가한다.
- 커밋·스쿼시 병합만 요청받았고 새 코드 변경·실패·충돌·검증 대상 차이가 없으면 기존 통과 결과를 재사용한다.
- 충돌을 해결했으면 해결로 달라진 동작을, 실패를 수정했으면 실패 항목과 수정의 영향을 받는 항목을 확인한다. 새 영향 근거
  없이 기존 통과 항목을 반복하지 않는다.
- 문서만 바꾸고 실행 코드·설정에 영향이 없으면 내용·링크·diff를 확인한다. 앱 테스트와 브라우저 검증은 실행하지 않는다.
- E2E의 언어·실행 설정만 바꾸고 시나리오·화면 동작을 유지했다면 타입 검사·모듈 로딩·변경한 실행 경로의 대표 사례를
  확인한다. 새 오류나 동작 차이가 발견되면 그 영향을 받는 범위를 추가한다.

선정 근거는 다음 관계로 짧게 남긴다. 기록을 위해 별도 계획 문서를 만들거나 영향 없는 모든 화면의 제외 사유를 나열하지
않는다.

| 변경 사항                | 영향받는 동작               | 선택한 검사 또는 재사용할 결과                   |
| ------------------------ | --------------------------- | ------------------------------------------------ |
| 이번 수정·충돌 해결 내용 | 직접 달라지는 동작과 사용처 | 해당 TC·검사 또는 대상이 일치하는 기존 통과 근거 |

### 3. 범위를 넓히는 조건

전체 검사나 추가 회귀 검사는 **사용자 요청, 프로젝트의 필수 검사, 확인된 광범위한 영향 또는 실패의 근거**가 있을 때만
선택한다. 넓혀야 할 이유와 추가할 대상을 정하고, 요청 범위에 필요한 검증은 재확인 없이 완료한다.

선정한 범위의 검증을 마쳤으면 그 결과로 완료 여부를 판단한다. 이번 변경과 관련 없는 전체 화면 회귀 검사를 남은 필수
작업으로 취급하거나, 실행하지 않았다는 사실만으로 미완료라고 보고하지 않는다.

## 화면 작업의 사용성 검증과 완료 기준

선택한 S·F의 기능 결과와 함께, 변경된 상호작용에서 실제로 발생할 수 있는 사용성 위험을 확인한다. 화면 전체의 항목을 매번
재검사하거나, 아래 조건의 모든 조합을 검사하지 않는다.

### 검사 전에 위험과 기대 결과 구체화

화면 진입·검색·탭·페이지·입력·저장·모달·뒤로 가기 중 변경에 해당하는 조작을 고르고, 필요한 위험을 TC에 적는다.

| 점검 관점        | 사용자 입장에서 확인할 것                                 |
| ---------------- | --------------------------------------------------------- |
| 시각적 연속성    | 깜빡임·빈 화면 노출·로딩 표시의 점멸·불필요한 배치 이동   |
| 반응과 진행 상태 | 입력·클릭의 즉시 반영, 대기 이유와 완료·실패 상태의 전달  |
| 조작의 연속성    | 입력값·커서·포커스·스크롤의 예기치 않은 초기화            |
| 상태의 일관성    | 선택 조건·데이터·건수·버튼 상태와 마지막 조작 의도의 일치 |
| 실패와 복구      | 오류 안내, 재시도·취소, 입력값과 작업 맥락의 보존         |
| 조작 가능성      | 필요한 동작의 키보드·좁은 화면 접근, 가림·잘림·중복 실행  |

특정 구현 방식 자체를 정답으로 삼지 않는다. TC에는 준비 조건·조작·진행 중 기대 결과·완료 또는 실패 후 기대 결과를
적는다.

### 선택한 조건에서 실제 조작 확인

- 격리된 headless Playwright를 사용한다. 정상·지연 응답, 첫 방문·재방문, 빠른 연속 조작, 실패·복구 중 해당 위험을
  드러내는 조건만 적용한다. 지연 응답이 필요하면 1~3초 등 기다리는 상태를 관찰할 수 있는 조건을 사용한다.
- 중간 상태가 검증 대상이면 DOM·위치·포커스 관찰, 영상·연속 프레임 중 적절한 근거를 남긴다. 최종 스크린샷만으로 조작 중
  깜빡임이나 배치 이동이 없었다고 판정하지 않는다.
- 자동 판정 가능한 회귀 항목은 재실행 가능한 검사로 남긴다. 도구로 판정하기 어려운 지각적 품질은 브라우저 관찰 근거를
  남긴다. 타입 검사·단위 테스트 결과로 화면 사용성 판정을 대신하지 않는다.

## 실패와 미확인 항목 처리

- 실패하면 원인을 수정하고 실패 항목과 수정으로 영향을 받은 항목을 다시 확인한다. 새 영향 근거 없이 기존 통과 항목을
  반복하지 않는다.
- 도구·환경 문제로 확인할 수 없으면 제한과 남은 항목을 기록한다. 실행 가능한 요청 범위의 검증은 완료하고, 미확인을
  통과로 바꾸지 않는다.
- 모의 API의 결과와 실제 서버·외부 서비스 연동 결과를 구분한다. 결정 대기·범위 제외·외부 연동 대기를 구현 실패나 검사
  통과와 섞지 않는다.

## 확인 기록과 완료 판정

선택한 TC와 해당 사용성 위험의 결과를 다음 형식으로 기록한다. 이번 작업의 대상이 아닌 화면까지 결과표를 확장하지 않는다.

| 항목·TC          | 판정                             | 근거 또는 사유                                                |
| ---------------- | -------------------------------- | ------------------------------------------------------------- |
| 확인 대상과 조건 | 통과 / 실패 / 미확인 / 해당 없음 | 자동 검사 또는 브라우저 관찰의 근거, 실행 제한 또는 제외 사유 |

- 검사 코드·실행 명령·관찰 자료 등 재확인할 근거를 남긴다. 기존 결과를 재사용했다면 해당 결과와 검증 대상의 일치 근거를
  표시한다.
- 실행 결과와 스크린샷·trace는 Git에서 제외한 로컬 결과 폴더에 보관한다. 개인 저장 위치는 로컬 지침에서 관리한다. 공유
  문서에는 TC·기준을, 공유 코드에는 재실행 가능한 검사를 남긴다.
- 완료 보고에서는 요청 범위의 구현·검증 결과, 남은 작업, 결정 대기·범위 제외 항목, 실제 연동·배포 상태를 구분한다.
  선택한 검사의 통과를 기능 전체나 실제 외부 연동의 완료로 확대하지 않는다.
- 필요한 검증은 개발 완료 보고 전에 마친다. CI는 이후 회귀를 감지하는 보조 수단이다. 이 문서 자체가 검사를 실행하거나
  CI를 차단하지는 않는다.
