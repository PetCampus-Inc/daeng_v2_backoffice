# 공지·약관 본문 블록 형식 합의 항목

작성일: 2026-10-22. 상태: **합의 준비 문서**. 아래 미확정 항목과 권장안은 서버·앱·BO의 합의 결과가 아니다.

목적은 공지·약관의 서식 편집을 시작하기 전에 저장 형식과 표시 규칙을 맞추는 것이다. 이 문서를 작성한 것으로 OQ-P4 보류가
해제되지는 않는다.

## 이미 결정된 내용과 확인 근거

| 구분           | 결정·관찰 내용                                                                | 근거·범위                                                                                    |
| -------------- | ----------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------- |
| 편집기         | 서식이 보이는 Plate 편집기를 사용한다                                         | PRD OQ-F3, 2026-10-21 결정                                                                   |
| 저장 방향      | 공지·약관 본문은 서버의 블록 JSON 형식을 유지한다                             | PRD 6.4·6.5, OQ-P4                                                                           |
| 서버 응답 관찰 | `schemaVersion: 1`, `blocks`, `paragraph`, `children`, `text` 형태가 관찰됐다 | PRD OQ-P4에 기록된 2026-10-21 운영 API 조회. 이번 문서 작업에서 운영 API를 재조회하지 않았다 |
| 앱 표시 관찰   | 기존 앱은 텍스트를 찾아 문단으로 표시하며 블록 종류·서식을 해석하지 않는다    | PRD OQ-P4의 front #744 분석 기록. 최신 앱 코드의 재검증 결과는 아니다                        |
| 공지 서식      | 문단·소제목·굵게·목록·표·링크·구분선·이미지                                   | PRD 7.8. 링크는 http·https만, 넓은 표는 표 내부 가로 스크롤, HTML은 글자로 표시              |
| 약관 서식      | 공지와 같은 서식에서 이미지 제외                                              | PRD 7.11                                                                                     |
| 이미지 정책    | 공지만 삽입. JPG·JPEG·PNG·HEIC·HEIF, 파일당 최대 20MB, 개수 제한 없음         | PRD 7.8 및 OQ-D2. 업로드 API 규격은 아직 이 문서로 확정하지 않는다                           |
| 약관 날짜      | 공개 시 KST 공고일과 입력 시행일을 `YYYY년 M월 D일`로 채운다                  | PRD 7.11. 본문 어디에 있는 자리표시자도 대상이며 새 버전 복제 시 날짜를 되돌린다             |

PRD 7.8에는 이전 마크다운 입력 방식의 설명이 남아 있다. 편집 방식은 이후 결정인 OQ-F3를 기준으로 보고, 서버 형식 합의 후
작성 폼 설명과 TC를 함께 갱신해야 한다.

관찰된 기존 문단 데이터의 최소 예시는 다음과 같다. 다른 서식의 필드명이나 현재 지원 가능한 전체 스키마를 뜻하지 않는다.

```json
{
  "schemaVersion": 1,
  "blocks": [{ "type": "paragraph", "children": [{ "text": "본문" }] }]
}
```

## 먼저 받아야 할 답변

아래 담당은 협의 제안이다. 실제 책임자·승인자는 별도로 정한다.

| 우선순위·항목       | 합의할 질문                                                                                                     | 합의 산출물                                               | 협의 제안  |
| ------------------- | --------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------- | ---------- |
| P0 형식의 기준      | 서버 표준 스키마를 두고 Plate와 변환할지, Plate 문서 구조를 저장 규격으로 채택할지? 스키마를 어디서 관리하는가? | 기준 문서·관리 저장소·책임자, 직렬화/역직렬화 책임        | 서버·BO·앱 |
| P0 버전·기존 데이터 | 기존 `schemaVersion: 1`을 확장하는가? 어떤 변경에서 버전을 올리는가? 기존 문단과 구형 앱은 어떻게 처리하는가?   | 버전별 읽기/쓰기 지원표, 이전 데이터 정책                 | 서버·앱·BO |
| P0 서식별 구조      | 아래 블록·인라인·텍스트 서식의 정확한 타입명·필드·중첩 규칙은 무엇인가?                                         | JSON Schema 또는 동등한 검증 규격과 서식별 유효/무효 예제 | 서버·BO·앱 |
| P0 저장·오류 계약   | 초안·공개 요청의 본문 필드, 크기 제한, 잘못된 구조·지원하지 않는 버전의 오류 코드와 위치 정보는 무엇인가?       | 요청/응답 예제, 오류 규격                                 | 서버·BO    |
| P0 앱 표시          | 앱이 각 블록과 서식을 어떻게 그리는가? 기존 앱이 새 본문을 받아도 되는가?                                       | 지원표·표시 예시·새 서식 쓰기 허용 시점                   | 앱·서버·BO |
| P0 약관 날짜        | 자리표시자를 텍스트로 유지하는가, 의미가 있는 별도 노드로 표현하는가? 공개·복제 시 누가 변환하는가?             | 초안→공개→새 버전 예제와 서버 처리 규칙                   | 서버·BO·앱 |
| P1 이미지           | 업로드 결과의 자산 식별자·원본/표시용 URL·변환 대기/실패·임시 파일 정리는 어떻게 표현하는가?                    | 공지 이미지 블록 및 업로드/변환 계약                      | 서버·BO·앱 |

P1은 중요도가 낮다는 뜻이 아니라 별도 업로드 계약과 연결된다는 뜻이다. **이미지를 포함한 공지 편집 완료에는 P1
합의·구현도 필요하다.** 약관에는 이미지를 추가하지 않는다.

## 서식별로 정의할 구조

아래는 필요한 표현 능력이다. `heading`, `bold` 등의 구체적 필드 이름을 새 규격으로 확정하지 않는다.

| 대상           | 필요한 합의                                                         | 공통 예제로 확인할 것                                            |
| -------------- | ------------------------------------------------------------------- | ---------------------------------------------------------------- |
| 문단·줄바꿈    | 문단 경계와 문단 내부 줄바꿈, 빈 문단·빈 문서 표현                  | 연속 빈 줄, 앞뒤 공백, 여러 줄 저장 후 그대로 다시 편집          |
| 굵게           | 텍스트 서식 저장 위치, 인접 텍스트 조각 병합 규칙                   | 한 문장의 중간만 굵게여도 앱에서는 한 문장으로 표시              |
| 소제목         | 허용하는 제목 단계와 본문과의 구분                                  | BO 미리보기와 앱에서 같은 제목 단계로 표시                       |
| 목록           | 순서 있음/없음 지원 범위, 항목·하위 문단·중첩 깊이·시작 번호        | 글머리표/번호 유지, 긴 항목 줄바꿈, 중첩 저장·복원               |
| 표             | 행·열·셀 구조, 헤더·병합 셀 지원 여부, 크기 제한, 셀 내부 허용 내용 | 여러 행·열, 빈 셀, 셀 내부 굵게/링크, 좁은 화면의 표 내부 스크롤 |
| 링크           | 주소와 표시문 저장 위치, 중첩 서식, 허용 URL 판정                   | 표시문·주소 보존, 굵게와 함께 사용, http·https 외 주소 거부      |
| 구분선         | 텍스트가 없는 블록의 표현과 허용 위치                               | 저장·조회·미리보기·앱에서 사라지지 않음                          |
| 이미지(공지만) | 자산 참조, 원본/변환본, 대체 텍스트, 크기·캡션 지원 여부            | HEIC·HEIF 변환본 표시, 로딩 실패, 글자 없는 이미지 블록 보존     |

표 병합, 목록 중첩, 캡션·대체 텍스트 등의 구체적 지원 범위는 질문이며, 이 문서에서 새 기능 요구사항으로 추가한 것이
아니다.

## 약관 날짜 치환에서 별도로 합의할 사례

단순히 각 텍스트 조각에 문자열 치환을 적용하면 서식 경계에서 날짜를 놓칠 수 있다. 아래 예제를 서버·BO·앱이 공유해야
한다.

1. 문단·목록 항목·표 셀 등 허용된 위치에 있는 `{{공고일}}`·`{{시행일}}`을 모두 채운다.
2. 자리표시자 중간에 굵게 등 서식이 나뉘어 여러 텍스트 조각에 저장돼도 한 자리표시자로 처리할지 정한다.
3. 실제 날짜가 같은 일반 문장과 자동 입력된 날짜를 복제 시 어떻게 구분할지 정한다. 날짜 문자열의 무차별 치환으로 다른
   내용까지 바뀌지 않아야 한다.
4. 초안에서는 자리표시자를 보존하고, 공개 시 KST 날짜를 채우며, 다시 새 버전을 만들면 자리표시자로 복구한다. 그 과정에서
   주변 서식을 보존한다.
5. 잘못된 자리표시자·직접 고친 날짜·일부 삭제된 날짜의 공개 허용 여부와 오류 안내를 정한다.
6. 공개 요청과 날짜 치환의 최종 책임을 정한다. 권장안은 서버가 공개 시각으로 최종 치환하고, BO 미리보기는 같은 규칙을
   재현하는 것이다.

## 현재 구현과 실제 연동 사이의 차이

| 영역 | 현재 작업 코드                                                 | 계약 확정 후 필요한 변경                                                             |
| ---- | -------------------------------------------------------------- | ------------------------------------------------------------------------------------ |
| 공지 | `NoticeBody`는 기존 문단 모양의 블록 JSON만 표현               | 확정된 서식 타입과 변환기·편집기·미리보기 적용                                       |
| 약관 | `Term.body`는 mock 범위의 일반 문자열. 날짜 치환도 문자열 기준 | 실제 서버의 블록 JSON 타입으로 교체, 편집/저장 변환과 구조를 보존하는 날짜 치환 적용 |
| 앱   | PRD 기록상 텍스트 탐색 후 문단 표시                            | 최신 구현 확인 후 블록 타입·텍스트 서식을 읽는 표시 기능 적용                        |

현재 약관 mock 문자열을 그대로 실제 저장 API에 보내도 된다는 의미가 아니다. 이 문서에서는 편집기 설치, 본문 타입 변경,
실제 API 연결을 수행하지 않는다.

## 담당별 전달할 요청

- **서버**: 기준 스키마와 서식별 JSON, 초안/공개 저장·오류 예제, 기존 데이터·버전 정책, 날짜 치환 책임을 확인해 주세요.
  공지 이미지는 업로드·변환 계약도 별도로 필요합니다.
- **앱**: 최신 표시 코드의 지원 범위를 확인하고, 공유 예제가 BO 미리보기와 같은 의미로 표시되도록 지원표와 적용 순서를
  정해 주세요.
- **BO**: 서버 규격↔Plate 변환, 공지/약관별 허용 도구, 본문 검증·날짜 처리·미리보기를 합의된 예제에 맞춰 구현합니다.
- **공동**: 계약 문서 관리 위치·변경 승인자와 구형 앱 호환 정책을 정합니다. 새 서식을 저장하기 전에 실제 앱이 읽을 수
  있는지 확인합니다.

이 문서는 전달 가능한 요청 초안이며 다른 담당자에게 실제로 발송하지 않았다.

## 보류 해제와 구현 완료 기준

**보류 해제**에는 P0 질문의 답, 서식별 유효/무효 예제, 앱 지원 범위와 적용 계획이 필요하다. 공지 이미지는 P1 계약도
필요하다. 답이 오면 PRD 7.8·7.11의 이전 설명과 TC 05·06의 OQ-P4 표시를 함께 정리한다.

**서식 구현 완료**는 별도다. 합의된 규격으로 다음을 확인한 뒤 보고한다.

- 기존 문단 데이터 조회·재저장과 새 서식 저장→조회→재편집에서 내용 손실이 없다.
- 문단·굵게·소제목·목록·표·링크·구분선이 BO와 실제 앱에서 일치한다. 이미지는 공지에서 별도로 확인한다.
- 한 문장 안 굵게, 표 셀 안 링크, 빈 문단 등 혼합 예제가 보존된다.
- 약관 초안→공개→복제에서 날짜와 주변 서식이 올바르다.
- 잘못된/미지원 구조·URL·크기 초과 요청과 실패 복구를 확인한다.
- 지연 저장, 연속 입력, 실제 조합 입력, 커서·선택·스크롤 유지, 툴바 키보드 조작을 화면 TC로 검증한다.
- mock 검증과 실제 API·앱 연동 검증을 구분한다. 배포 여부도 별도로 기록한다.
